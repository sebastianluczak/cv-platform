= Architecture Drivers

This project began as a learning and portfolio application. Its architecture reflects an evolving prototype rather than a production-ready service.

== Drivers

=== Product drivers

* Accept a resume file from a browser and return promptly rather than keeping the user request open during extraction.
* Support both text-based PDFs and scanned/image-based resumes.
* Keep the initial backend workflow small and observable while it evolves.

=== Technical drivers

* Use Go for backend services and React for the browser UI.
* Use RabbitMQ for asynchronous job delivery and S3-compatible storage for uploaded files and extraction results.
* Use Server-Sent Events (SSE) to deliver processing progress to the browser.
* Capture consequential architecture choices in ADRs and publish documentation with Antora.

== Trade-offs and constraints

* Asynchronous processing keeps HTTP uploads separate from extraction latency, but requires durable job handling and status delivery.
* The current status store is in-memory and single-instance oriented; it is not a resilient multi-replica status service.
* Resume files and extracted text are persisted without service-managed expiration. Retention, authentication, and production hardening remain deployment concerns.
* Skill matching and AI weighting are not yet integrated into the implemented workflow.

== Architecture practices

ADRs capture selected decisions, while the architecture and service pages describe the current implementation. These should be revised together as component boundaries or runtime behavior change.
