= Processing Workflow

== Successful upload and extraction

. A client sends `POST /upload` with a multipart field named `file`.
. The uploader accepts PDF, PNG, JPEG, TIFF, or BMP content up to 10 MiB. It detects the content type from the uploaded bytes.
. The uploader generates a UUID, stores the original at `uploads/<job-id>`, and publishes a persistent JSON message to `QUEUE_NAME`.
. The uploader waits for RabbitMQ's publisher confirmation before returning HTTP `202 Accepted` with the job ID.
. The extractor consumes the message with manual acknowledgement and prefetch set to one. It downloads the object, extracts text, and writes `results/<job-id>.txt`.
. The extractor publishes a persistent redaction job to `QUEUE_NAME.pii`; it acknowledges the extraction job only after RabbitMQ confirms that publish.
. Piistripper reads the extraction result, writes a separate `results/<job-id>.redacted.txt` copy, publishes `completed`, and acknowledges the redaction job. The uploader consumes status events and updates its in-memory store.
. The client connects to `GET /events?job_id=<job-id>`. SSE sends the current snapshot first, then subsequent updates, with a 20-second keep-alive comment.

== Extraction failures and retries

The extractor gives each job a five-minute processing timeout. A failed extraction is republished to the work queue with an incremented `x-retry-count`, then the original delivery is acknowledged. Piistripper similarly retries redaction failures.
The initial attempt plus up to three retries means a job may be attempted four times at each stage. During redaction retries the status remains `redacting` and includes a retry message, keeping the UI progress step accurate.

A job still failing extraction is published to `QUEUE_NAME.failed`; a job still failing redaction is published to `QUEUE_NAME.pii.failed`.

Malformed job JSON is also sent directly to the failed queue. 

== Delivery semantics

The workflow is **at-least-once**, not exactly-once. 

If a service stops between a side effect and acknowledgement, RabbitMQ can redeliver a job. 

Result writes use deterministic keys (`results/<job-id>.txt` and `results/<job-id>.redacted.txt`), so repeated successful processing overwrites the corresponding object. The redacted copy does not replace the original extracted text.

There is no separate deduplication store, operation is idempotent.

=== SSE status durability

SSE status events are **not a durable history for clients**: 

. they are consumed by the `uploader`,
. retained only in **that** `uploader` process. 

A reconnect to the same live instance receives the latest snapshot, but an `uploader` **after restart** or **another replica** will not have the job's status.

IMPORTANT: This is serious and needs proper addressing.
