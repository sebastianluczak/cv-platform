= Processing Workflow

== Successful upload and extraction

. A client sends `POST /upload` with a multipart field named `file`.
. The uploader accepts PDF, PNG, JPEG, TIFF, or BMP content up to 10 MiB. It detects the content type from the uploaded bytes.
. The uploader generates a UUID, stores the original at `uploads/<job-id>`, and publishes a persistent JSON message to `QUEUE_NAME`.
. The uploader waits for RabbitMQ's publisher confirmation before returning HTTP `202 Accepted` with the job ID.
. The extractor consumes the message with manual acknowledgement and prefetch set to one. It downloads the object, extracts text, and writes `results/<job-id>.txt`.
. On success, the extractor publishes a `completed` event and acknowledges the job. The uploader consumes status events and updates its in-memory store.
. The client connects to `GET /events?job_id=<job-id>`. SSE sends the current snapshot first, then subsequent updates, with a 20-second keep-alive comment.

== Extraction failures and retries

The extractor gives each job a five-minute processing timeout. A failed extraction is republished to the work queue with an incremented `x-retry-count`, then the original delivery is acknowledged. The initial attempt plus up to three retries means a job may be attempted four times. A job still failing after those attempts is published to `QUEUE_NAME.failed` and acknowledged from the work queue.

Malformed job JSON is also sent directly to the failed queue. Queue republishes use publisher confirms and persistent messages. Status publishing is best-effort: a status publish failure is logged but does not prevent processing or acknowledgement.

== Delivery semantics

The workflow is at-least-once, not exactly-once. If a service stops between a side effect and acknowledgement, RabbitMQ can redeliver a job. Result writes use a deterministic key (`results/<job-id>.txt`), so a repeated successful extraction overwrites that object's key. There is no separate deduplication store.

SSE status events are not a durable history for clients: they are consumed by the uploader and retained only in that uploader process. A reconnect to the same live instance receives the latest snapshot, but an uploader restart or another replica may not have the job's status.
