= Data and Persistence

== Stored data

[cols="1,2,2,2"]
|===
|Data |Location |Key or lifetime |Current behavior

|Original resume
|Configured S3-compatible bucket
|`uploads/<job-id>`
|Written by the uploader before the job is queued. No deletion or object lifecycle policy is implemented in these services.

|Extracted text
|Same bucket
|`results/<job-id>.txt`
|Written by the extractor after extraction. No retrieval or deletion endpoint is implemented here.

|Extraction job
|RabbitMQ work queue
|`QUEUE_NAME`
|Persistent message in a durable queue; manually acknowledged after success, retry republish, or failed-queue republish.

|Failed job
|RabbitMQ failed queue
|`QUEUE_NAME.failed`
|Persistent message retained for inspection or operator-managed requeue. No requeue tooling is included.

|Processing status
|RabbitMQ status queue, then uploader memory
|`QUEUE_NAME.events`; in memory for at most 24 hours and up to 10,000 jobs per uploader process
|The uploader consumes and acknowledges status messages. Its status history is lost when the process restarts.
|===

== Temporary files

The extractor downloads each input to a temporary file. For scanned PDFs it renders pages to temporary PNG files before OCR. The code removes these files after processing, but temporary data exists on the extractor host while a job is running.

== Retention and privacy

The services do not implement a retention schedule for uploaded resumes or extracted text. Storage administrators must configure lifecycle expiration and access controls appropriate to their data policy. The current implementation therefore must not be described as never storing personal data: resumes and their extracted text are persisted in object storage.

The `aiweighter` prototype also sends its input text to the OpenRouter API if invoked. It is not connected to this pipeline, but its use would disclose that content to an external provider; see xref:services:prototypes.adoc[prototype components].
