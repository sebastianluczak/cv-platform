CV Platform

2026-10-14

Overview

CV Platform (also presented as Draftline in the UI) is an early-stage resume-processing application.

  1. A user submits a resume;

  2. the backend stores the original,

  3. backend queues an extraction job,

  4. system makes processing updates available to the browser.

Architecture

Architecture Drivers

This project began as a learning and portfolio application. Its architecture reflects an evolving prototype rather than a production-ready service.

Drivers

Product drivers

  • Accept a resume file from a browser and return promptly rather than keeping the user request open during extraction.

  • Support both text-based PDFs and scanned/image-based resumes.

  • Keep the initial backend workflow small and observable while it evolves.

Technical drivers

  • Use Go for backend services and React for the browser UI.

  • Use RabbitMQ for asynchronous job delivery and S3-compatible storage for uploaded files and extraction results.

  • Use Server-Sent Events (SSE) to deliver processing progress to the browser.

  • Capture consequential architecture choices in ADRs and publish documentation with Antora.

Component responsibilities

Component Responsibility

Browser UI

Selects an allowed file, posts it as multipart form data, then listens to status updates using EventSource.

Uploader

Validates and stores the uploaded file, publishes a persistent extraction job, and streams the latest in-memory status to clients using Server-Sent Events (SSE).

Extractor

Consumes jobs, downloads the referenced upload, extracts PDF or image text, stores the result, and acknowledges or routes the job according to its outcome.

RabbitMQ

Carries extraction jobs, status events, and terminal failed jobs in durable queues.

S3-compatible storage

Stores the original upload and extracted plain text. Both services must use the same bucket and endpoint configuration.

Processing workflow

Successful upload and extraction

  1. A client sends POST /upload with a multipart field named file.

  2. The uploader accepts PDF, PNG, JPEG, TIFF, or BMP content up to 10 MiB. It detects the content type from the uploaded bytes.

  3. The uploader generates a UUID, stores the original at uploads/<job-id>, and publishes a persistent JSON message to QUEUE_NAME.

  4. The uploader waits for RabbitMQ’s publisher confirmation before returning HTTP 202 Accepted with the job ID.

  5. The extractor consumes the message with manual acknowledgement and prefetch set to one. It downloads the object, extracts text, and writes results/<job-id>.txt.

  6. The extractor publishes a persistent redaction job to QUEUE_NAME.pii; it acknowledges the extraction job only after RabbitMQ confirms that publish.

  7. Piistripper reads the extraction result, writes a separate results/<job-id>.redacted.txt copy, publishes completed, and acknowledges the redaction job. The uploader consumes status events and updates its in-memory store.

  8. The client connects to GET /events?job_id=<job-id>. SSE sends the current snapshot first, then subsequent updates, with a 20-second keep-alive comment.

Extraction failures and retries

The extractor gives each job a five-minute processing timeout. A failed extraction is republished to the work queue with an incremented x-retry-count, then the original delivery is acknowledged. Piistripper similarly retries redaction failures. The initial attempt plus up to three retries means a job may be attempted four times at each stage. During redaction retries the status remains redacting and includes a retry message, keeping the UI progress step accurate.

A job still failing extraction is published to QUEUE_NAME.failed; a job still failing redaction is published to QUEUE_NAME.pii.failed.

Malformed job JSON is also sent directly to the failed queue.

Delivery semantics

The workflow is at-least-once, not exactly-once.

If a service stops between a side effect and acknowledgement, RabbitMQ can redeliver a job.

Result writes use deterministic keys (results/<job-id>.txt and results/<job-id>.redacted.txt), so repeated successful processing overwrites the corresponding object. The redacted copy does not replace the original extracted text.

There is no separate deduplication store, operation is idempotent.

SSE status durability

SSE status events are not a durable history for clients:

  1. they are consumed by the uploader,

  2. retained only in that uploader process.

A reconnect to the same live instance receives the latest snapshot, but an uploader after restart or another replica will not have the job’s status.

This is serious and needs proper addressing.

Temporary files

The extractor downloads each input to a temporary file. For scanned PDFs it renders pages to temporary PNG files before OCR. The code removes these files after processing, but temporary data exists on the extractor host while a job is running.

Retention and privacy

The services do not implement a retention schedule for uploaded resumes, extracted text, or redacted results. The redacted result is not guaranteed to be anonymous, and the original extracted text remains unchanged.

Storage administrators must configure lifecycle expiration and access controls appropriate to their data policy.

This is obvious - we will use Antora for internal documentation.

ADR-0003: Use of RabbitMQ for asynchronous communication

Microservices in this project will use RabbitMQ for asynchronous communication.

Context

In a microservices architecture, services need a channel and a language to communicate with each other.

Synchronous communication (e.g., HTTP REST) can lead to tight coupling and increased latency, while asynchronous communication allows services to operate independently and handle messages at their own pace.

Decision

This project uses RabbitMQ as the message broker for asynchronous communication between microservices.

Consequences

Payloads will be sent as messages to RabbitMQ queues, and services will consume these messages asynchronously.

References

  • [RabbitMQ](https://www.rabbitmq.com/)

  • [RabbitMQ Tutorials](https://www.rabbitmq.com/getstarted.html)

ADR-0004: Use of SSE for user-level notifications

Traditionally, a web page has to send a request to the server to receive new data; that is, the page requests data from the server. With server-sent events, it’s possible for a server to send new data to a web page at any time, by pushing messages to the web page. These incoming messages can be treated as Events + data inside the web page.

Context

In this project, all jobs are asynchronous. User only truly waits for data upload and the process starts.

As it progresses, we want real status updates for user in UI.

Decision

This project uses SSE to communicate with the client.

Consequences

Browser creates a session with SSE.

Prototype components

Uploader

The uploader is the HTTP entry point for file submissions. It stores originals in object storage, publishes extraction jobs to RabbitMQ, and serves processing updates as SSE.

HTTP endpoints

POST /upload accepts multipart form data with a file field. Supported detected media types are application/pdf, image/png, image/jpeg, image/tiff, and image/bmp; the file limit is 10 MiB.

Response Meaning

202 Accepted

The object was stored and RabbitMQ confirmed the extraction job. JSON contains job_id and status: "queued".

400 Bad Request

The multipart upload is invalid or its file cannot be read.

405 Method Not Allowed

The request method is not POST.

413 Content Too Large

The file exceeds the upload limit.

415 Unsupported Media Type

The detected content type is not supported.

500 Internal Server Error

The uploader could not store or process the upload.

503 Service Unavailable

RabbitMQ did not confirm the extraction job.

The upload body is limited to 10 MiB plus 64 KiB for multipart framing. The uploader writes the original object before publishing the job. If publishing fails, the stored object is not automatically removed.

GET /events?job_id=<job-id> streams status event JSON in SSE data: frames. It returns 404 if the uploader has no retained status for that job. The latest snapshot is sent immediately; terminal completed and failed states end the stream. Clients may reconnect while the status remains in the same uploader process.

Runtime behavior

At startup the uploader creates an S3-compatible client, checks for the configured bucket and creates it if absent, connects to RabbitMQ, declares the durable work queue, and consumes the durable <QUEUE_NAME>.events queue.

Status is held in memory for at most 24 hours, with a capacity of 10,000 jobs. The oldest status may be evicted when the capacity is reached. The store rejects invalid stages, stale updates after a terminal state, and a later queued event for an existing job.

Run one uploader instance for the current queue-based SSE design. Status queue consumers compete for messages, and each instance has a separate in-memory store; multiple replicas are not a broadcast arrangement.

Operational notes

The listener uses PORT, defaulting to 8080. The service does not define a health-check endpoint or persistent status store. See configuration and operations.

Extractor

The extractor consumes JSON jobs from RabbitMQ, downloads the referenced upload, extracts text, stores the result, and queues redaction.

Extraction behavior

  • For PDFs, it first runs pdftotext with layout preservation and UTF-8 output. If the result is blank, it reads the page count with pdfinfo, renders pages at 200 DPI with pdftoppm, and runs Tesseract OCR on each page.

  • For PNG, JPEG, TIFF, and BMP inputs, it runs Tesseract OCR directly.

  • It writes non-empty extracted text as UTF-8 plain text to results/<job-id>.txt.

The extractor validates that the job ID is non-empty, the bucket equals its configured bucket, and the object key is exactly uploads/<job-id>. Each processing attempt has a five-minute timeout.

Acknowledgement, retry, and failure

The consumer uses manual acknowledgements and a prefetch of one.

  1. On success it publishes a persistent redaction job to QUEUE_NAME.pii and acknowledges the extraction delivery only after publisher confirmation.

  2. On processing failure it publishes a retrying status and republishes the job with an incremented x-retry-count and after publisher confirmation it acknowledges the original.

It makes up to three retries after the initial attempt. After the last failed attempt, or for malformed JSON, it republishes the message to QUEUE_NAME.failed and acknowledges the original.

Retry and failed-queue republishing use publisher confirms. If a republish cannot be confirmed, the original delivery is negatively acknowledged and requeued. A terminal failed status is published on exhausted extraction attempts.

Extraction status publishing is best-effort. Once extraction succeeds, the job is not marked complete: piistripper publishes the terminal completed status after writing the redacted copy.

Runtime requirements

The extractor requires pdftotext, pdfinfo, and pdftoppm on PATH, plus the Tesseract runtime and language data used by the gosseract binding. The provided Dockerfile installs Poppler utilities on top of the otiai10/gosseract image.

The extractor checks the PDF tools at startup, then connects to RabbitMQ and object storage. See configuration and operations.

Local environment is properly configured with NixOS packages.

PII stripper

The piistripper consumes durable redaction jobs from QUEUE_NAME.pii and reads the extracted text from the shared S3-compatible bucket. After successful redaction it writes results/<job-id>.redacted.txt; it does not overwrite or delete results/<job-id>.txt.

Detection and output

The service runs without external model/API calls. It applies local patterns for email addresses, URLs, phone numbers, and common street-address forms, plus the local English named-entity recognizer in github.com/jdkato/prose/v2 for person and organization names. It replaces matches with typed placeholders such as [EMAIL], [ADDRESS], [PERSON], and [ORGANIZATION].

This is best-effort redaction, not guaranteed anonymization. The English-only entity recognizer and patterns can miss direct, contextual, or indirect identifiers and can produce false positives. The separate original text remains personal data and is still subject to the applicable access-control and retention/deletion policy. Do not describe this service alone as GDPR compliance.

Delivery and failure behavior

The extractor publishes the redaction job only after storing the extracted result and acknowledges its original queue delivery only after RabbitMQ confirms the redaction publish. Piistripper validates that the job ID is a UUID, the bucket matches its configured bucket, and the object key is exactly results/<job-id>.txt.

The worker uses manual acknowledgements, a prefetch of one, deterministic output keys, a 10 MiB source-result limit, and up to three retries after the initial attempt. It republishes exhausted or malformed jobs to QUEUE_NAME.pii.failed. Terminal progress is published to QUEUE_NAME.events; the user-facing job becomes completed only after the redacted output is stored. Delivery is at-least-once, so duplicate work may occur.

Configuration

Piistripper shares RABBITMQ_URL, QUEUE_NAME, and all RUSTFS_* settings with the uploader and extractor. It reads objects from RUSTFS_BUCKET; deployment credentials should be limited to reading the extracted result and writing the redacted result. See configuration and operations.

Service contracts

Extraction job

The uploader publishes a persistent JSON message to QUEUE_NAME after storing the upload and confirming the publish:

{
  "id": "<job-id>",
  "bucket": "cv-platform-uploads",
  "object_key": "uploads/<job-id>",
  "content_type": "application/pdf"
}

id is a generated UUID. The extractor requires the bucket to match its configured RUSTFS_BUCKET and requires object_key to equal uploads/<id>.

Redaction job

After storing results/<id>.txt, the extractor publishes a persistent job to QUEUE_NAME.pii:

{
  "id": "<job-id>",
  "bucket": "cv-platform-uploads",
  "object_key": "results/<job-id>.txt"
}

Piistripper requires a UUID id, the configured bucket, and the exact result key derived from that ID. On success it writes the redacted copy to results/<id>.redacted.txt; the source result is retained. Exhausted and malformed redaction jobs are sent to QUEUE_NAME.pii.failed.

Status event

The extractor and piistripper publish status messages to the durable QUEUE_NAME.events queue. The uploader consumes these messages and retains the latest one per job in memory.

{
  "job_id": "<job-id>",
  "stage": "processing",
  "message": "We're reading your resume.",
  "attempt": 1,
  "updated_at": "2026-10-14T04:26:44Z"
}

Stages are queued, processing, retrying, redacting, completed, and failed. The extractor reports extraction activity; piistripper reports redaction and terminal completion/failure. updated_at is UTC. attempt is the attempt number represented by the status; queued is first recorded by the uploader after job publish confirmation.

Upload response

{
  "job_id": "<job-id>",
  "status": "queued"
}

The browser subscribes to /events?job_id=<job-id> and receives status event objects as SSE data frames.

Status updates are not a durable client-facing event log.

Operations

Prerequisites

The development environment is defined by devenv.nix and provides Go, Node.js, Antora, RabbitMQ, and RustFS. The extractor also needs Tesseract and Poppler tools (pdftotext, pdfinfo, and pdftoppm). RabbitMQ and RustFS are started by devenv up in the configured development environment.

Copy .env.dist to .env and provide appropriate local values before starting the environment. The repository template includes the RabbitMQ URL and queue name; storage settings default in the services. Never put production secrets in the template.

Start and build

From the repository root:

devenv up

The devenv processes start the uploader, extractor, piistripper, frontend, and documentation builder.

The service Dockerfiles expect prebuilt binaries named uploader, extractor, and piistripper in their respective service directories. task services:uploader:build, task services:extractor:build, and task services:piistripper:build build the binaries and Docker images.

Verification

Run the service unit tests from the repository root:

sh test.sh

Build the Antora site with task docs:build-docs.

Troubleshooting

  • Uploader does not start: check RABBITMQ_URL, QUEUE_NAME, storage endpoint/credentials, and whether the configured bucket can be listed or created.

  • Extractor does not start: verify RabbitMQ settings and that pdftotext, pdfinfo, and pdftoppm are available. Confirm the S3 settings point to the same bucket as the uploader.

  • No redacted result appears: confirm piistripper is running with the same QUEUE_NAME and RUSTFS_* settings; inspect its logs and the durable <QUEUE_NAME>.pii.failed queue.

  • Upload returns 503: inspect uploader logs and RabbitMQ availability; a message publish confirmation did not arrive.

  • No SSE update appears: confirm that the extractor can publish to QUEUE_NAME.events and that the uploader is consuming that queue. Status state is local to the uploader instance and does not survive its restart.

  • A job repeatedly fails: inspect the extractor logs and the durable QUEUE_NAME.failed queue.

Prototype components

Skill matcher

services/skillmatcher currently contains only a README describing an intended post-extraction skill-matching step. There is no Go implementation, input/output contract, executable, or connection from the extractor. Skill matching is not part of the running workflow.

AI weighter

services/aiweighter/aiweighter.go contains a standalone helper that sends supplied text to OpenRouter’s chat-completions endpoint. It selects a model directly in source and prints the response content, reasoning field, and full response body. It requires OPENROUTER_API_KEY and panics on errors.

This package is not wired into the upload/extraction flow, has no service module or independently declared Go module, and should be treated as experimental code rather than a production service. If invoked with resume text, it sends that content to an external provider. Review data handling, provider terms, error behavior, model configuration, and logging before integrating it.

Before connecting a prototype

Define an explicit input/output contract, ownership of retries and failures, privacy and retention behavior, and operational configuration. Update the architecture and data-lifecycle pages when the running service boundaries change.

Security

Data Security (PII)

The upload, extraction, and redaction services process resume data, which may contain personal information.

They persist the original file, extracted text, and a separate best-effort redacted copy in the configured S3-compatible bucket.

Current implementation

  • The uploader, extractor, and piistripper use static S3 credentials from environment variables; local-development defaults are rustfsadmin / rustfsadmin.

  • Uploaded objects are stored under uploads/<job-id> and extracted text under results/<job-id>.txt.

  • Piistripper writes results/<job-id>.redacted.txt without modifying or deleting the extracted source.

  • Piistripper performs local pattern matching and English named-entity recognition; it does not call a hosted model/API. Detection can miss direct, contextual, or indirect identifiers and can produce false positives.

  • The services do not implement deletion, expiration, or a retention policy for stored objects.

  • Temporary extractor files are created on the service host during processing and removed when processing finishes.

  • The uploader’s HTTP endpoints do not implement authentication or authorization.

Deployment responsibilities

Before handling real resumes, operators must configure:

  1. private storage access,

  2. dedicated least-privilege credentials,

  3. transport and network protections,

  4. an explicit retention/deletion policy.

Protect the uploader behind an authenticated and appropriately restricted network boundary.
Do not use development credentials in a deployed environment.
A redacted result is not guaranteed anonymization or GDPR compliance. Since the original extracted text is retained, it remains personal data and must continue to receive appropriate access control and retention/deletion handling. Obtain privacy/legal review before relying on this processing for a compliance obligation.
