Overview

CV Platform (also presented as Draftline in the UI) is an early-stage resume-processing application.

  1. A user submits a resume;

  2. the backend stores the original,

  3. backend queues an extraction job,

  4. system makes processing updates available to the browser.

Architecture

Architecture Drivers

This project began as a learning and portfolio application. Its architecture reflects an evolving prototype rather than a production-ready service.

Drivers

Product drivers

  • Accept a resume file from a browser and return promptly rather than keeping the user request open during extraction.

  • Support both text-based PDFs and scanned/image-based resumes.

  • Keep the initial backend workflow small and observable while it evolves.

Technical drivers

  • Use Go for backend services and React for the browser UI.

  • Use RabbitMQ for asynchronous job delivery and S3-compatible storage for uploaded files and extraction results.

  • Use Server-Sent Events (SSE) to deliver processing progress to the browser.

  • Capture consequential architecture choices in ADRs and publish documentation with Antora.

The UI is a separate React application.

  1. uses /api/upload and /api/events, so a deployment must route those browser paths to the uploader’s /upload and /events handlers.

  2. uses /offer-api and /ai-api for offer matching and AI resume generation in local development; production gateways must route those paths to the corresponding service APIs.

Component responsibilities

Component Responsibility

Browser UI

Selects an allowed file, posts it as multipart form data, then listens to status updates using EventSource.

Uploader

Validates and stores the uploaded file, publishes a persistent extraction job, and streams the latest in-memory status to clients using Server-Sent Events (SSE).

Extractor

Consumes jobs, downloads the referenced upload, extracts PDF or image text, stores the result, and acknowledges or routes the job according to its outcome.

AIweighter

After explicit user consent, sends the redacted resume, skill evidence, and retained offer text to the configured external model and stores a Markdown resume result.

RabbitMQ

Carries extraction jobs, status events, and terminal failed jobs in durable queues.

S3-compatible storage

Stores the original upload and extracted plain text. Both services must use the same bucket and endpoint configuration.

Processing workflow

Successful upload and extraction

  1. A client sends POST /upload with a multipart field named file.

  2. The uploader accepts PDF, PNG, JPEG, TIFF, or BMP content up to 10 MiB. It detects the content type from the uploaded bytes.

  3. The uploader generates a UUID, stores the original at uploads/<job-id>, and publishes a persistent JSON message to QUEUE_NAME.

  4. The uploader waits for RabbitMQ’s publisher confirmation before returning HTTP 202 Accepted with the job ID.

  5. The extractor consumes the message with manual acknowledgement and prefetch set to one. It downloads the object, extracts text, and writes results/<job-id>.txt.

  6. The extractor publishes a persistent redaction job to QUEUE_NAME.pii; it acknowledges the extraction job only after RabbitMQ confirms that publish.

  7. Piistripper reads the extraction result and writes a separate results/<job-id>.redacted.txt copy. It publishes a confirmed job to QUEUE_NAME.skills and acknowledges the redaction job after the publish is confirmed.

  8. The skill matcher reads the redacted text, scores it against deterministic role-profile patterns, writes results/<job-id>.skills.json, publishes completed, and acknowledges the matching job. The uploader consumes status events and updates its in-memory store.

  9. The client connects to GET /events?job_id=<job-id>. SSE sends the current snapshot first, then subsequent updates, with a 20-second keep-alive comment.

  10. After completion, the UI retrieves the persisted score artifact from GET /results?job_id=<job-id>.

Offer comparison

  1. After a resume score is loaded, the UI submits POST /matches to the offer matcher with the completed resume job ID and either pasted offer text or a public offer URL.

  2. The offer matcher publishes a persistent job to QUEUE_NAME.offers and returns 202 Accepted with a separate offer-match ID after publisher confirmation.

  3. The worker reads results/<resume-job-id>.skills.json. For URLs it fetches bounded static HTML from public HTTP(S) destinations, parses visible text, and does not store the fetched page.

  4. It finds required skill patterns in explicitly required/must-have sections. If no such section exists, it uses all detected skill patterns in the offer. It writes an unscorable result if no patterns are detected; otherwise it writes rounded percentage coverage plus matched/missing skill evidence to results/<offer-match-id>.offer.json.

  5. The offer result retains bounded normalized offer text for later AI tailoring; GET /matches/<offer-match-id> omits this private field.

  6. The UI polls GET /matches/<offer-match-id> until the result is completed, unscorable, or failed.

Optional AI resume generation

  1. After a completed offer match, the UI explains that the redacted resume, skill evidence, and job-offer text will be sent to OpenRouter.

  2. The user must explicitly opt in before the UI submits POST /weights with the offer-match ID and consent affirmation.

  3. AIweighter publishes a persistent ID-only job to QUEUE_NAME.aiweight and returns an AI resume ID. The worker reads the redacted resume, skill result, and bounded normalized offer text from storage, then requests a Markdown resume from the configured model.

  4. The worker stores the versioned result at results/<weigh-id>.ai.json; the UI polls GET /weights/<weigh-id> and displays the returned Markdown as text for review or download.

  5. The prompt instructs the model to use only source-supported facts and omit unsupported qualifications, dates, achievements, or metrics. User-provided resume and offer content is treated as untrusted data, not instructions.

Extraction failures and retries

The extractor gives each job a five-minute processing timeout. A failed extraction is republished to the work queue with an incremented x-retry-count, then the original delivery is acknowledged. Piistripper and the skill matcher similarly retry processing failures. The initial attempt plus up to three retries means a job may be attempted four times at each stage. During redaction retries the status remains redacting and includes a retry message, keeping the UI progress step accurate.

A job still failing extraction is published to QUEUE_NAME.failed; a job still failing redaction is published to QUEUE_NAME.pii.failed; a job still failing skill matching is published to QUEUE_NAME.skills.failed. A job still failing offer matching is published to QUEUE_NAME.offers.failed. A job still failing AI resume generation is published to QUEUE_NAME.aiweight.failed.

Malformed job JSON is also sent directly to the failed queue.

Delivery semantics

The workflow is at-least-once, not exactly-once.

If a service stops between a side effect and acknowledgement, RabbitMQ can redeliver a job.

Result writes use deterministic keys (results/<job-id>.txt, results/<job-id>.redacted.txt, results/<job-id>.skills.json, and results/<offer-match-id>.offer.json), so repeated successful processing overwrites the corresponding object. The redacted copy does not replace the original extracted text.

There is no separate deduplication store, operation is idempotent.

SSE status durability

SSE status events are not a durable history for clients:

  1. they are consumed by the uploader,

  2. retained only in that uploader process.

A reconnect to the same live instance receives the latest snapshot, but an uploader after restart or another replica will not have the job’s status.

This is serious and needs proper addressing.

The extractor downloads each input to a temporary file. For scanned PDFs it renders pages to temporary PNG files before OCR. The code removes these files after processing, but temporary data exists on the extractor host while a job is running.

Datacleaner service

The datacleaner service runs on a configurable interval (default: every 1 minute) to maintain data retention policies. It is stateless and does not participate in the main processing pipeline.

Purpose and scope

The datacleaner service performs two primary functions:

  1. S3 cleanup: Scans and deletes expired objects from configured S3-compatible storage:

    • Original uploaded files (uploads/<job-id>) after RETENTION_UPLOADS_DAYS days

    • Redacted text results (results/<job-id>.redacted.txt) after RETENTION_REDACTED_DAYS days

  2. RabbitMQ failed queue cleanup: Purges expired messages from failed queues:

    • <QUEUE_NAME>.extraction.failed

    • <QUEUE_NAME>.pii.failed

    • <QUEUE_NAME>.skills.failed

    • Other stage-specific failed queues

Messages are deleted after RETENTION_FAILED_QUEUE_DAYS days, allowing operators time to inspect and manually requeue failures if needed.

Cleanup interval and dry-run mode

The service runs cleanup cycles at a configurable interval (CLEANUP_INTERVAL_MINUTES, default: 1 minute). Each cycle:

  1. Scans S3 for expired objects

  2. Deletes expired S3 objects (unless DRY_RUN=true)

  3. Scans failed queues for expired messages

  4. Purges expired messages (unless DRY_RUN=true)

  5. Logs metrics and any errors

For testing and policy validation, the DRY_RUN environment variable logs what would be deleted without making any changes.

RabbitMQ failed queue retention

Failed messages (messages that exhausted retry attempts) are retained in dedicated failed queues for operator inspection. The datacleaner periodically purges messages older than RETENTION_FAILED_QUEUE_DAYS:

  • Operators can manually requeue failed messages for retry before expiration

  • After the retention period, messages are automatically deleted

  • The retention window allows time for incident investigation and diagnostics

See Processing workflow for details on failure handling and retry semantics.

Operator configuration for production

Deploying datacleaner and configuring retention policies for production requires careful planning:

Required S3 permissions

The datacleaner service requires the following S3 IAM permissions on the configured bucket:

  • s3:ListBucket: List objects to identify candidates for deletion

  • s3:DeleteObject: Delete expired uploads and redacted text files

{

    }

Compliance and data retention

Before deploying datacleaner to production, verify that configured retention periods comply with applicable data protection and privacy regulations:

  • Extracted text (results/<job-id>.txt) and skill results are not automatically deleted. If these contain personal data, configure S3 lifecycle policies separately or rely on datacleaner for redacted text cleanup only.

  • Redaction is best-effort: The redacted text may still contain sensitive information. Review redaction quality and retention periods in the context of your data protection obligations.

  • Original uploads are deleted after RETENTION_UPLOADS_DAYS. Ensure this period aligns with user expectations and legal requirements.

Testing retention policies

Before deploying to production, test retention policies using dry-run mode:

export DRY_RUN=true
export RETENTION_UPLOADS_DAYS=7
export RETENTION_REDACTED_DAYS=7
export RETENTION_FAILED_QUEUE_DAYS=7
./datacleaner

Dry-run mode logs what would be deleted without modifying S3 or RabbitMQ. Verify that the logged deletions match your intended retention policy.

Additional retention considerations

The offer matcher does not persist fetched offer HTML. Pasted offer text is carried in its durable RabbitMQ message until processing; configure queue retention accordingly. The offer matcher API has no user authorization or ownership model, so deployments must keep it behind an access-controlled boundary.

After a user opts in, normalized offer text and generated Markdown persist as result artifacts, and the redacted resume and skill result are sent to the configured external OpenRouter model. Redaction is best-effort and does not guarantee anonymity. AIweighter and offermatcher do not implement authentication or ownership checks; keep both APIs behind an access-controlled boundary. Configure object-store lifecycle and access controls for all resume, offer, and AI output artifacts.

Storage administrators must configure lifecycle expiration and access controls appropriate to their data policy. Review Data Security (PII) for additional security and privacy considerations.

Data retention policy

Overview

The datacleaner service implements automatic deletion of personal data according to configured retention policies. This guide is intended for operators, deployment engineers, and compliance teams responsible for running and maintaining the CV platform.

The datacleaner service runs on a configurable interval (default 1 minute) to clean up expired data from the object store and message queues. It supports dry-run mode for testing and verification without making permanent deletions.

Purpose

The datacleaner service exists to:

  • Automatically delete personal data (resumes, extracted text, and results) after their retention period expires

  • Minimize unnecessary storage of personally identifiable information (PII)

  • Provide compliance support for privacy regulations (GDPR, CCPA, and similar)

  • Offer operators an inspection window for failed jobs before automatic purge

Key characteristics

  • Runs independently on a configurable interval

  • Operates on S3-compatible object stores and RabbitMQ message queues

  • Supports dry-run mode for safe testing before production deployment

  • Logs all deletion operations for audit trails

  • Deletes data after retention periods expire; does not reprocess incomplete jobs

Important notes on retention

  • Redaction is best-effort only and is not guaranteed to produce anonymized data. Original extracted text and redacted versions should both be treated as personal data.

  • Original uploaded files are deleted after the retention period regardless of processing success. If extraction or redaction failed, the resume cannot be reprocessed from the object store; the client must re-upload.

  • Offer text and AI-generated content are retained together with the underlying resume data they reference.

  • Failed queue messages provide an inspection window for operators to review errors before automatic deletion.

Deployment Checklist

Before deploying datacleaner to production, ensure the following steps are completed:

Pre-deployment verification

  • Review data retention policy with legal and compliance teams

  • Confirm retention timelines align with organizational privacy requirements (GDPR, CCPA, etc.)

  • Document any exceptions or custom retention periods in your deployment guide

Infrastructure and access control

  • Configure S3 credentials with DeleteObject and ListBucket permissions

  • Verify S3 bucket exists and is accessible from the datacleaner host

  • Verify RabbitMQ URL and credentials are correct

  • Test S3 and RabbitMQ connectivity before deployment

  • Ensure sufficient IAM/authorization scopes to purge failed queues (if applicable)

Environment and configuration

  • Set retention period environment variables (see Configuration Reference)

  • Set cleanup interval (default 1 minute may be too aggressive; consider 10-60 minutes in production)

  • Configure S3 credentials (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, S3_ENDPOINT, S3_BUCKET)

  • Configure RabbitMQ URL and queue names

  • Enable logging to an appropriate level (debug for initial deployment, info for production)

Testing and validation

  • Test in dry-run mode first (DRY_RUN=true) to verify configuration and see what would be deleted

  • Review dry-run logs to ensure retention logic is working as expected

  • Perform a small manual test (upload a resume, wait for processing, verify in dry-run mode)

  • Monitor logs for successful cleanup operations in dry-run mode

  • Verify that S3 objects and RabbitMQ messages are NOT actually deleted during dry-run

Production deployment

  • Disable dry-run mode (DRY_RUN=false)

  • Deploy datacleaner service

  • Monitor logs for at least the first 24 hours

  • Verify that old data is being deleted as expected

  • Set up alerting for datacleaner errors or failures

  • Plan for audit logging of all deletions (optional but recommended)

Ongoing operations

  • Review and tune cleanup interval based on data volume and performance

  • Monitor S3 and RabbitMQ performance impact

  • Maintain audit logs of deletions for compliance

  • Verify failed queue messages are purged after retention expires

Operational Procedures

Enable dry-run mode for testing

To test the datacleaner without permanently deleting data:

# Set dry-run mode
export DRY_RUN=true

# Start the datacleaner service
./datacleaner

# Monitor logs for deletion operations
tail -f datacleaner.log | grep -E "would delete|DELETE|removing"

# Review what would be deleted
grep "would delete" datacleaner.log | wc -l
Review cleanup logs

Logs contain detailed information about what was deleted and why:

# Show all deletion operations
grep "DELETE\|removed" datacleaner.log

# Show deletions by type
grep "S3.*DELETE" datacleaner.log      # Object store deletions
grep "RabbitMQ.*DELETE" datacleaner.log # Message queue purges

# Count deletions by date
grep "DELETE" datacleaner.log | cut -d' ' -f1 | sort | uniq -c
Manually delete data before retention expires

In cases where immediate deletion is required (e.g., user GDPR right-to-be-forgotten requests):

# Set dry-run mode first to preview
export DRY_RUN=true
export FORCE_DELETE_JOB_ID=<job-id>

./datacleaner

# If the preview looks correct, disable dry-run
export DRY_RUN=false
./datacleaner
Manual deletion should only be performed by authorized operators and should be logged and audited.
Pause or resume the datacleaner service

To temporarily stop automatic cleanup (e.g., during investigation):

# Stop the datacleaner process
sudo systemctl stop datacleaner

# Verify it is stopped
sudo systemctl status datacleaner

# Resume cleanup
sudo systemctl start datacleaner

Compliance Considerations

Privacy and data protection

  • Redaction is best-effort, not guaranteed anonymization. The piistripper service removes obvious PII patterns but may miss context-dependent information. Both original and redacted text should be treated as personal data.

  • Original extracted text remains personal data. The unredacted results/<job-id>.txt file is deleted immediately after redaction, but during processing it contains potentially sensitive information. Treat extraction logs and intermediate states as sensitive.

  • Failed jobs provide inspection window. Failed queue messages are retained for a configurable period (default 7 days) to allow operators to investigate errors. Review and delete failed messages on schedule to minimize PII retention.

  • Deleted data cannot be recovered. Once the datacleaner removes an object or message, it is permanently gone. Maintain backups if recovery may be needed for compliance investigations.

GDPR / CCPA compliance

Before deploying datacleaner, your organization should:

  1. Review and document data processing. Confirm that automatic deletion aligns with your Data Processing Agreement and privacy policy.

  2. Define retention periods. Work with legal and compliance teams to determine appropriate retention periods for your use case (not necessarily 7 days).

  3. Implement subject access and deletion rights. The datacleaner automates expiration-based deletion, but you must also support user requests to delete their data on demand.

  4. Maintain audit trails. Log all deletion operations for compliance investigations and audits. See Setup audit logging.

  5. Notify users. Ensure privacy documentation and user-facing policies accurately describe how and when their data is deleted.

  6. Handle failures gracefully. Failed jobs are retained to allow inspection; ensure your procedures delete them within the retention window.

Setup audit logging

To maintain compliance audit trails, configure logging to a persistent storage system:

# Example: write datacleaner logs to syslog and a file
datacleaner 2>&1 | tee -a /var/log/datacleaner.log | logger -t datacleaner -p local0.info

# Compress and archive older logs
logrotate /etc/logrotate.d/datacleaner

Include deletion logs in your compliance reports and backup them according to your record retention policy.

Troubleshooting

Cleanup is slow or not keeping up

Symptom: Storage usage continues to grow; old data is not being deleted fast enough.

Diagnosis: * Check cleanup interval: is CLEANUP_INTERVAL_MINUTES too large? * Check S3 performance: high latency or timeouts? * Check RabbitMQ queue depth: are there many old failed messages?

Resolution:

# Reduce cleanup interval for more aggressive deletion
CLEANUP_INTERVAL_MINUTES=5

# Or increase performance
# - Use S3 list pagination to reduce API calls
# - Increase batch size for message deletions
# - Check S3 and RabbitMQ connection limits

# Monitor performance
journalctl -u datacleaner -f | grep -E "duration|completed|DELETE"
Permission denied errors

Symptom: Logs contain AccessDenied or PermissionDenied errors.

Diagnosis: * S3 credentials lack DeleteObject permission? * RabbitMQ user lacks purge or delete permissions? * S3 bucket policy blocks the datacleaner principal?

Resolution:

# Verify S3 credentials
aws s3 ls s3://<bucket>/uploads/ --endpoint-url <S3_ENDPOINT>

# Test delete permission (use dry-run first)
DRY_RUN=true ./datacleaner

# Check RabbitMQ user permissions
rabbitmqctl list_user_permissions <user>

# Update IAM policy with DeleteObject permission (AWS S3):
# {
#   "Effect": "Allow",
#   "Action": ["s3:GetObject", "s3:DeleteObject", "s3:ListBucket"],
#   "Resource": ["arn:aws:s3:::bucket-name", "arn:aws:s3:::bucket-name/*"]
# }
Messages not purging from failed queues

Symptom: Messages accumulate in <QUEUE_NAME>.failed and are not deleted after retention expires.

Diagnosis: * RabbitMQ connection lost or queue name mismatch? * Retention period is set to 0 or disabled? * Failed queue has a message TTL that conflicts with datacleaner?

Resolution:

# Verify RabbitMQ connectivity
rabbitmq-diagnostics check_running
rabbitmq-diagnostics check_alarms

# Check failed queue configuration
rabbitmqctl list_queues name durable arguments

# Verify retention config is set
echo $RETENTION_FAILED_QUEUE_DAYS

# Manually purge a queue (if necessary)
rabbitmqctl purge_queue <QUEUE_NAME>.failed
Missing data or unexpected deletion

Symptom: Data that should have been retained was deleted early, or needed data is missing.

Diagnosis: * Was dry-run mode properly configured for testing? * Was manual deletion triggered by mistake? * Are there multiple datacleaner processes running?

Resolution:

# Stop the datacleaner to prevent further deletions
sudo systemctl stop datacleaner

# Review logs to identify what was deleted
grep -E "DELETE|removed" datacleaner.log | tail -100

# Check backups
aws s3 sync s3://<bucket-backup>/uploads/ . --dry-run

# Restore from backups if necessary
aws s3 sync <local-backup>/ s3://<bucket>/uploads/

# Verify only one datacleaner is running
ps aux | grep datacleaner

# Resume after investigation
sudo systemctl start datacleaner
Always maintain backups and test restore procedures before deploying the datacleaner to production.

ADR-0003: Use of RabbitMQ for asynchronous communication

Microservices in this project will use RabbitMQ for asynchronous communication.

Context

In a microservices architecture, services need a channel and a language to communicate with each other.

Synchronous communication (e.g., HTTP REST) can lead to tight coupling and increased latency, while asynchronous communication allows services to operate independently and handle messages at their own pace.

Decision

This project uses RabbitMQ as the message broker for asynchronous communication between microservices.

Consequences

Payloads will be sent as messages to RabbitMQ queues, and services will consume these messages asynchronously.

Traditionally, a web page has to send a request to the server to receive new data; that is, the page requests data from the server. With server-sent events, it’s possible for a server to send new data to a web page at any time, by pushing messages to the web page. These incoming messages can be treated as Events + data inside the web page.

As it progresses, we want real status updates for user in UI.

This project uses SSE to communicate with the client.

ADR-0006: Cost-aware GitHub Actions without reducing assurance

Context

The project reported spending 350 of its 2,000 free GitHub Actions minutes in one day. A review of the latest 24 hours of workflow runs found:

  • CI ran 33 times: 27 pull request runs and 6 pushes to main.

  • Documentation publication ran 33 times on the same events.

  • AI review ran 12 times on pull request updates.

  • The Go security scan ran 5 times. Each run started five matrix jobs, and each job spent approximately 42–66 seconds installing the same pinned gosec version.

The CI and documentation workflows both set up Nix and devenv. The documentation workflow builds a preview on every pull request, including changes that cannot affect the documentation. The CI workflow uses devenv test, which currently runs the four Go test suites in test.sh; it does not run UI tests, docs, or the common module.

The GitHub run-usage endpoint returned zero billed milliseconds for sampled runs, so the timings above are runner step durations and run counts, not a precise reconstruction of billed minutes. Existing checks, review feedback, SARIF uploads, documentation previews, and production publication must remain available for relevant changes.

Decision

Preserve the current CI and AI-review triggers and all existing check coverage. Reduce repeat work where the affected output is clear:

  1. Keep the documentation workflow and its pull request job/check active, but run the expensive documentation build and preview only when documentation sources or their build configuration changed. Restrict main push runs to those same paths. Keep manual dispatch able to build documentation.

  2. Build the pinned gosec binary once per security workflow run and distribute it to the existing five-module matrix. Keep the per-module job names, scan scope, SARIF files, categories, and uploads. Cache each module’s Go dependencies using its go.sum.

  3. Continue running devenv test for all current CI triggers. Do not broaden or reduce its test coverage as part of this cost change.

Documentation-affecting paths are docs/**, taskfile.yml, devenv.nix, devenv.yaml, devenv.lock, and .github/workflows/publish-antora.docs.yml.

Consequences

Unrelated pull requests still produce a successful documentation workflow check, but skip Nix/devenv installation and documentation build steps. Changes to docs or build configuration continue to generate previews, and relevant pushes to main continue to publish the production site.

The security workflow adds one setup job and artifact transfer, but avoids compiling the same security tool independently in five runners. The matrix remains parallel and keeps its existing check names; the setup job becomes a prerequisite.

CI and AI review may continue to run for changes that do not affect their results. This is intentional until branch-protection requirements and broader code/test dependencies are verified; path-based CI skipping could otherwise remove a required status check or miss a dependency.

Measure billed minutes and check results after adoption. If documented paths, outputs, required checks, or scan categories are missing, restore the prior behavior before pursuing further trigger narrowing.

Uploader

The uploader is the HTTP entry point for file submissions. It stores originals in object storage, publishes extraction jobs to RabbitMQ, and serves processing updates as SSE.

HTTP endpoints

POST /upload accepts multipart form data with a file field. Supported detected media types are application/pdf, image/png, image/jpeg, image/tiff, and image/bmp; the file limit is 10 MiB.

Response Meaning

202 Accepted

The object was stored and RabbitMQ confirmed the extraction job. JSON contains job_id and status: "queued".

400 Bad Request

The multipart upload is invalid or its file cannot be read.

405 Method Not Allowed

The request method is not POST.

413 Content Too Large

The file exceeds the upload limit.

415 Unsupported Media Type

The detected content type is not supported.

500 Internal Server Error

The uploader could not store or process the upload.

503 Service Unavailable

RabbitMQ did not confirm the extraction job.

The upload body is limited to 10 MiB plus 64 KiB for multipart framing. The uploader writes the original object before publishing the job. If publishing fails, the stored object is not automatically removed.

GET /events?job_id=<job-id> streams status event JSON in SSE data: frames. It returns 404 if the uploader has no retained status for that job. The latest snapshot is sent immediately; terminal completed and failed states end the stream. Clients may reconnect while the status remains in the same uploader process.

GET /results?job_id=<job-id> serves the stored JSON role-match result for a valid UUID job ID. It returns 404 if the result artifact does not exist and rejects invalid IDs before reading object storage.

Runtime behavior

At startup the uploader creates an S3-compatible client, checks for the configured bucket and creates it if absent, connects to RabbitMQ, declares the durable work queue, and consumes the durable <QUEUE_NAME>.events queue.

Status is held in memory for at most 24 hours, with a capacity of 10,000 jobs. The oldest status may be evicted when the capacity is reached. The store rejects invalid stages, stale updates after a terminal state, and a later queued event for an existing job.

Run one uploader instance for the current queue-based SSE design. Status queue consumers compete for messages, and each instance has a separate in-memory store; multiple replicas are not a broadcast arrangement.

Operational notes

The listener uses PORT, defaulting to 8080. The service does not define a health-check endpoint or persistent status store. See configuration and operations.

Extractor

The extractor consumes JSON jobs from RabbitMQ, downloads the referenced upload, extracts text, stores the result, and queues redaction.

Extraction behavior

  • For PDFs, it first runs pdftotext with layout preservation and UTF-8 output. If the result is blank, it reads the page count with pdfinfo, renders pages at 200 DPI with pdftoppm, and runs Tesseract OCR on each page.

  • For PNG, JPEG, TIFF, and BMP inputs, it runs Tesseract OCR directly.

  • It writes non-empty extracted text as UTF-8 plain text to results/<job-id>.txt.

The extractor validates that the job ID is non-empty, the bucket equals its configured bucket, and the object key is exactly uploads/<job-id>. Each processing attempt has a five-minute timeout.

Acknowledgement, retry, and failure

The consumer uses manual acknowledgements and a prefetch of one.

  1. On success it publishes a persistent redaction job to QUEUE_NAME.pii and acknowledges the extraction delivery only after publisher confirmation.

  2. On processing failure it publishes a retrying status and republishes the job with an incremented x-retry-count and after publisher confirmation it acknowledges the original.

It makes up to three retries after the initial attempt. After the last failed attempt, or for malformed JSON, it republishes the message to QUEUE_NAME.failed and acknowledges the original.

Retry and failed-queue republishing use publisher confirms. If a republish cannot be confirmed, the original delivery is negatively acknowledged and requeued. A terminal failed status is published on exhausted extraction attempts.

Extraction status publishing is best-effort. Once extraction succeeds, the job is not marked complete: piistripper queues matching after writing the redacted copy, and the skill matcher publishes terminal completed only after storing role scores.

Runtime requirements

The extractor requires pdftotext, pdfinfo, and pdftoppm on PATH, plus the Tesseract runtime and language data used by the gosseract binding. The provided Dockerfile installs Poppler utilities on top of the otiai10/gosseract image.

The extractor checks the PDF tools at startup, then connects to RabbitMQ and object storage. See configuration and operations.

Local environment is properly configured with NixOS packages.

PII stripper

The piistripper consumes durable redaction jobs from QUEUE_NAME.pii and reads the extracted text from the shared S3-compatible bucket. After successful redaction it writes results/<job-id>.redacted.txt; it does not overwrite or delete results/<job-id>.txt.

Detection and output

The service runs without external model/API calls. It applies local patterns for email addresses, URLs, phone numbers, and common street-address forms, plus the local English named-entity recognizer in github.com/jdkato/prose/v2 for person and organization names. It replaces matches with typed placeholders such as [EMAIL], [ADDRESS], [PERSON], and [ORGANIZATION].

This is best-effort redaction, not guaranteed anonymization. The English-only entity recognizer and patterns can miss direct, contextual, or indirect identifiers and can produce false positives. The separate original text remains personal data and is still subject to the applicable access-control and retention/deletion policy. Do not describe this service alone as GDPR compliance.

Delivery and failure behavior

The extractor publishes the redaction job only after storing the extracted result and acknowledges its original queue delivery only after RabbitMQ confirms the redaction publish. Piistripper validates that the job ID is a UUID, the bucket matches its configured bucket, and the object key is exactly results/<job-id>.txt.

The worker uses manual acknowledgements, a prefetch of one, deterministic output keys, a 10 MiB source-result limit, and up to three retries after the initial attempt. It republishes exhausted or malformed jobs to QUEUE_NAME.pii.failed. After storing redacted text, it publishes a confirmed job to QUEUE_NAME.skills; the skill matcher later publishes terminal completed after storing scores. Delivery is at-least-once, so duplicate work may occur.

Configuration

Piistripper shares RABBITMQ_URL, QUEUE_NAME, and all RUSTFS_* settings with the uploader, extractor, and skill matcher. It reads objects from RUSTFS_BUCKET; deployment credentials should be limited to reading the extracted result and writing the redacted result. See configuration and operations.

Skill matcher

The skill matcher consumes jobs after PII stripping, reads the redacted text from shared S3-compatible storage, and scores the resume against deterministic IT role-profile patterns. It does not call an external model or API.

Workflow and result

The service consumes persistent JSON jobs from QUEUE_NAME.skills:

{
  "id": "<job-id>",
  "bucket": "cv-platform-uploads",
  "object_key": "results/<job-id>.redacted.txt"
}

The worker validates the UUID, configured bucket, and exact object key. It reads no more than 10 MiB of text and writes a versioned result to results/<job-id>.skills.json. The result includes the job ID, scoring timestamp, categories, integer scores, and matched patterns as evidence. The uploader serves this JSON at GET /results?job_id=<job-id>.

Piistripper publishes the matching job only after storing the redacted text. The matcher publishes matching, followed by terminal completed only after storing the score result. It uses manual acknowledgements, a prefetch of one, publisher confirms, and up to three retries after the initial attempt. Exhausted and malformed jobs are published to QUEUE_NAME.skills.failed. Delivery is at-least-once; deterministic object keys make repeated writes safe.

Categories and scoring rubric

V1 includes backend, DevOps, management, architecture, QA, frontend, data, and security. Each category counts distinct matching patterns:

Matched patterns Score Interpretation

0-1

1

Little or no matching evidence

2-3

2

Some matching evidence

4-5

3

Moderate matching evidence

6-7

4

Strong matching evidence

8 or more

5

Broad matching evidence

These scores are heuristic indicators of text signals, not objective measures of candidate ability or suitability. Matched patterns are included so results can be interpreted. The scorer does not use identity or demographic characteristics.

Configuration and operation

RABBITMQ_URL and QUEUE_NAME are required. The matcher must use the same RUSTFS_ENDPOINT_URL, RUSTFS_BUCKET, RUSTFS_REGION, RUSTFS_ACCESS_KEY_ID, and RUSTFS_SECRET_ACCESS_KEY values as the uploader and preceding workers. See configuration.

Run locally with task services:skillmatcher:start; build the binary and Docker image with task services:skillmatcher:build. For retry and queue operations, see local operations.

Offer matcher

The offer matcher compares the active resume’s stored skill evidence with an offer supplied as text or as a public, server-rendered HTML page. It produces deterministic required-skill keyword coverage; it does not evaluate candidate ability or suitability.

Workflow and API

The UI submits POST /matches after the resume’s results/<resume-job-id>.skills.json artifact is available. The JSON body contains resume_job_id and exactly one of offer_text or offer_url. The service validates the request, publishes a persistent job to QUEUE_NAME.offers with publisher confirmation, and returns 202 Accepted with a separate match_id.

Poll GET /matches/<match-id> for queued, processing, completed, unscorable, or failed status. The completed artifact is stored at results/<match-id>.offer.json. It contains a rounded percentage, required and matched counts, and matched/missing patterns. No detected required patterns produces an unscorable status instead of a 0% score.

The result artifact retains bounded normalized offer text for the optional AIweighter flow. GET /matches/<match-id> deliberately omits that private field.

Matching behavior

Offer and resume evidence use the shared curated pattern vocabulary also used by the skill matcher. The worker extracts patterns from an explicit required/must-have section when present; otherwise it uses patterns detected throughout the offer. Coverage is round(100 * matched distinct patterns / required distinct patterns). This keyword heuristic can miss unsupported wording and may treat related aliases as different patterns.

URL and privacy boundaries

URL fetches allow only HTTP(S) on default ports, enforce time, redirect, and response-size limits, reject credentials and private/reserved destinations, validate DNS addresses, and dial only validated public IP addresses. HTTPS redirects cannot downgrade to HTTP. Ordinary static HTML is supported; client-rendered pages are not. The service extracts HTML text in memory and does not store the fetched page.

Pasted offer text remains in a durable RabbitMQ message until processed. The worker reads the existing resume skill artifact, not the original resume. Because the API has no authentication or account ownership checks, deployments must place it behind an access-controlled boundary.

Configuration and operations

Set the shared RABBITMQ_URL, QUEUE_NAME, and RUSTFS_* configuration. OFFERMATCHER_PORT defaults to 8081. The worker consumes QUEUE_NAME.offers, uses manual acknowledgements, prefetch one, publisher confirms, and up to three retries after the initial attempt. Exhausted or malformed jobs go to QUEUE_NAME.offers.failed. See configuration and local operations.

AIweighter

AIweighter prepares an optional Markdown resume tailored to a completed resume and offer match. The UI requests generation only after an explicit user action and discloses that the redacted resume, skill evidence, and offer text will be sent to an external OpenRouter model. Generated content is limited to source-supported facts; the model is instructed to omit unsupported claims. Users should review the result before using it.

API and data flow

The UI submits POST /weights with the completed offer-match ID and consent: true. The service verifies the referenced offer-match artifact is complete, writes a queued state to results/<weigh-id>.ai.json, and publishes an ID-only persistent job to QUEUE_NAME.aiweight with publisher confirmation. It returns 202 Accepted with the new weigh_id. The stored request artifact records the consent affirmation and timestamp.

Poll GET /weights/<weigh-id> for queued, processing, completed, or failed. Completed results include a Markdown field. The UI displays it as plain text and offers a .md download rather than rendering model output as HTML.

The worker reads results/<resume-job-id>.redacted.txt, results/<resume-job-id>.skills.json, and the bounded normalized offer text stored in results/<offer-match-id>.offer.json. Offer text is excluded from the public offer-match status response. Original resume uploads and unredacted extraction text are not sent to the model.

Provider, queue, and privacy

OPENROUTER_API_KEY is required. OPENROUTER_MODEL selects the model and defaults to nvidia/nemotron-3-super-120b-a12b:free. AIweighter uses the shared RABBITMQ_URL, QUEUE_NAME, and RUSTFS_* configuration; its HTTP port is AIWEIGHTER_PORT (default 8082).

The consumer uses manual acknowledgements, prefetch one, publisher confirms, and up to three retries after the initial attempt. Malformed and exhausted jobs go to QUEUE_NAME.aiweight.failed. The workflow is at-least-once and uses a deterministic artifact key.

The job queue carries only IDs, but the model request includes redacted resume text, skills, and offer text. Redaction is best-effort, and generated Markdown and retained offer text have no application-enforced retention schedule. Configure object-store lifecycle and access controls. AIweighter and offermatcher have no authentication or ownership model; keep both APIs behind an access-controlled boundary. Consent is not authorization.

Run locally with task services:aiweighter:start; build with task services:aiweighter:build. See configuration and local operations. The Vite development proxy uses /ai-api; production deployments must route the UI’s VITE_AIWEIGHTER_ENDPOINT to the AIweighter HTTP API.

Offer matching

After a resume’s skill result is ready, the client submits an offer comparison:

{
  "resume_job_id": "<completed-resume-job-uuid>",

Status event

The extractor and piistripper publish status messages to the durable QUEUE_NAME.events queue. The uploader consumes these messages and retains the latest one per job in memory.

Operations

Prerequisites

The development environment is defined by devenv.nix and provides Go, Node.js, Antora, RabbitMQ, and RustFS. The extractor also needs Tesseract and Poppler tools (pdftotext, pdfinfo, and pdftoppm). RabbitMQ and RustFS are started by devenv up in the configured development environment.

Copy .env.dist to .env and provide appropriate local values before starting the environment. The repository template includes the RabbitMQ URL and queue name; storage settings default in the services. Never put production secrets in the template.

Start and build

From the repository root:

devenv up

The devenv processes start the uploader, extractor, piistripper, skill matcher, offer matcher, AIweighter, frontend, and documentation builder.

The service Dockerfiles expect prebuilt binaries named uploader, extractor, piistripper, skillmatcher, offermatcher, and aiweighter in their respective service directories. task services:uploader:build, task services:extractor:build, task services:piistripper:build, task services:skillmatcher:build, task services:offermatcher:build, and task services:aiweighter:build build the binaries and Docker images.

Verification

Run the service unit tests from the repository root:

sh test.sh

Build the Antora site with task docs:build-docs.

Troubleshooting

  • Uploader does not start: check RABBITMQ_URL, QUEUE_NAME, storage endpoint/credentials, and whether the configured bucket can be listed or created.

  • Extractor does not start: verify RabbitMQ settings and that pdftotext, pdfinfo, and pdftoppm are available. Confirm the S3 settings point to the same bucket as the uploader.

  • No redacted result appears: confirm piistripper is running with the same QUEUE_NAME and RUSTFS_* settings; inspect its logs and the durable <QUEUE_NAME>.pii.failed queue.

  • No role scores appear: confirm piistripper and skillmatcher are running with matching RabbitMQ/storage settings; inspect the durable <QUEUE_NAME>.skills.failed queue and the skillmatcher logs.

  • Offer comparison does not complete: confirm the frontend can reach the offer matcher on OFFERMATCHER_PORT, that the service shares the resume’s RUSTFS_BUCKET, and inspect <QUEUE_NAME>.offers.failed. Public offer pages only are supported; private-network destinations, non-HTML content, and SPA-rendered pages are rejected or unsupported.

  • AI resume generation does not complete: confirm the UI can reach AIweighter on AIWEIGHTER_PORT, OPENROUTER_API_KEY is configured, the model name is valid, the service shares the same bucket, and inspect <QUEUE_NAME>.aiweight.failed.

  • Upload returns 503: inspect uploader logs and RabbitMQ availability; a message publish confirmation did not arrive.

  • No SSE update appears: confirm that the extractor can publish to QUEUE_NAME.events and that the uploader is consuming that queue. Status state is local to the uploader instance and does not survive its restart.

  • A job repeatedly fails: inspect the extractor logs and the durable QUEUE_NAME.failed queue.

Security

Data Security (PII)

The upload, extraction, and redaction services process resume data, which may contain personal information.

They persist the original file, extracted text, and a separate best-effort redacted copy in the configured S3-compatible bucket.

Current implementation

  • The uploader, extractor, and piistripper use static S3 credentials from environment variables; local-development defaults are rustfsadmin / rustfsadmin.

  • Uploaded objects are stored under uploads/<job-id> and extracted text under results/<job-id>.txt.

  • Piistripper writes results/<job-id>.redacted.txt without modifying or deleting the extracted source.

  • Piistripper performs local pattern matching and English named-entity recognition; it does not call a hosted model/API. Detection can miss direct, contextual, or indirect identifiers and can produce false positives.

  • The skill matcher reads only the separately stored redacted text and applies local deterministic patterns; it does not send resume content to a hosted model/API. Its result stores category scores and matched pattern evidence, and redaction is not guaranteed anonymization.

  • Temporary extractor files are created on the service host during processing and removed when processing finishes.

  • The uploader’s HTTP endpoints do not implement authentication or authorization.

  • The datacleaner service implements automated data lifecycle management with configurable retention periods and dry-run mode for testing.

Deployment responsibilities

Before handling real resumes, operators must configure:

  1. private storage access,

  2. dedicated least-privilege credentials (including DeleteObject permission for the datacleaner service),

  3. transport and network protections,

  4. the datacleaner service with appropriate retention periods based on compliance requirements.

The datacleaner service automatically enforces retention policies by scanning the configured S3 bucket and deleting expired objects. Retention periods and cleanup frequency must be configured to align with GDPR, CCPA, or other applicable compliance obligations.

Protect the uploader behind an authenticated and appropriately restricted network boundary.
Do not use development credentials in a deployed environment.
A redacted result is not guaranteed anonymization or GDPR compliance. Datacleaner service must be properly configured and monitored to ensure compliance obligations are met. Obtain privacy/legal review before relying on this processing for a compliance obligation.

Datacleaner service

The datacleaner service implements automated data lifecycle management to enforce retention policies:

  • Runs on a configurable schedule (default: every minute).

  • Scans the configured S3-compatible bucket for objects matching known patterns (uploads/<job-id>, results/<job-id>.txt, results/<job-id>.redacted.txt, results/<job-id>.skills.json, etc.).

  • Deletes expired objects based on their age and configured retention periods.

  • Supports per-object-type retention overrides (e.g., keep skill results longer than extracted text).

  • Dry-run mode available for testing: operators can verify deletion behavior before enabling actual deletion.

  • Logs all deletion operations, including object key, deletion timestamp, and reason (age exceeds retention period).

  • Supports automatic purging of failed RabbitMQ messages (e.g., QUEUE_NAME.failed, QUEUE_NAME.pii.failed) after a configurable retention period.

Operators must ensure the datacleaner’s S3 credentials have the DeleteObject permission and that RabbitMQ access is configured for queue purge operations.

Security considerations

  • Redaction is best-effort: Pattern matching and named-entity recognition can miss contextual, indirect, or domain-specific identifiers. A redacted result does not guarantee anonymization.

  • Original extracted text is automatically deleted: The datacleaner service deletes the original extracted text (results/<job-id>.txt) after the configured retention period expires. This reduces exposure time for personal data compared to indefinite retention.

  • Failed messages are auto-purged: Operator-configured retention policy on failed queues prevents indefinite storage of job messages containing job IDs and metadata. This applies to QUEUE_NAME.failed and all stage-specific failed queues (e.g., QUEUE_NAME.pii.failed, QUEUE_NAME.skills.failed).

  • Dry-run mode recommended: Operators should test the datacleaner service in dry-run mode to verify that the retention policy matches compliance requirements before enabling production deletion.

  • Temporary files are cleaned up: The extractor removes temporary files (OCR PDFs, extracted text copies) after processing finishes, but temporary data exists on the host during job processing.

Operational security notes

The datacleaner service improves compliance posture but requires operator diligence:

  • Monitor cleanup logs: Regularly review datacleaner logs to verify that deletion operations execute as expected. Failed deletions should trigger alerts.

  • Verify deletion success: Confirm that objects are actually deleted from storage and that no deletion errors are suppressed in logs.

  • Audit trail: Ensure deletion operations are logged with sufficient detail (object key, timestamp, reason) to support audit and compliance reviews.

  • Alert on failures: Configure alerting on cleanup job failures, S3 permission errors, or unexpected retention patterns.

  • Credential rotation: Regularly rotate S3 credentials used by the datacleaner service; follow principle of least privilege.

  • Compliance review: Before production deployment, conduct a privacy and legal review to ensure the retention policy aligns with GDPR, CCPA, and other applicable regulations.

The redacted result is still not guaranteed anonymization; coordinate retention policies with legal/privacy teams.
