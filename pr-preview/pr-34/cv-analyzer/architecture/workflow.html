Processing Workflow

Successful upload and extraction

  1. A client sends POST /upload with a multipart field named file.

  2. The uploader accepts PDF, PNG, JPEG, TIFF, or BMP content up to 10 MiB. It detects the content type from the uploaded bytes.

  3. The uploader generates a UUID, stores the original at uploads/<job-id>, and publishes a persistent JSON message to QUEUE_NAME.

  4. The uploader waits for RabbitMQ’s publisher confirmation before returning HTTP 202 Accepted with the job ID.

  5. The extractor consumes the message with manual acknowledgement and prefetch set to one. It downloads the object, extracts text, and writes results/<job-id>.txt.

  6. The extractor publishes a persistent redaction job to QUEUE_NAME.pii; it acknowledges the extraction job only after RabbitMQ confirms that publish.

  7. Piistripper reads the extraction result and writes a separate results/<job-id>.redacted.txt copy. It publishes a confirmed job to QUEUE_NAME.skills and acknowledges the redaction job after the publish is confirmed.

  8. The skill matcher reads the redacted text, scores it against deterministic role-profile patterns, writes results/<job-id>.skills.json, publishes completed, and acknowledges the matching job. The uploader consumes status events and updates its in-memory store.

  9. The client connects to GET /events?job_id=<job-id>. SSE sends the current snapshot first, then subsequent updates, with a 20-second keep-alive comment.

  10. After completion, the UI retrieves the persisted score artifact from GET /results?job_id=<job-id>.

Offer comparison

  1. After a resume score is loaded, the UI submits POST /matches to the offer matcher with the completed resume job ID and either pasted offer text or a public offer URL.

  2. The offer matcher publishes a persistent job to QUEUE_NAME.offers and returns 202 Accepted with a separate offer-match ID after publisher confirmation.

  3. The worker reads results/<resume-job-id>.skills.json. For URLs it fetches bounded static HTML from public HTTP(S) destinations, parses visible text, and does not store the fetched page.

  4. It finds required skill patterns in explicitly required/must-have sections. If no such section exists, it uses all detected skill patterns in the offer. It writes an unscorable result if no patterns are detected; otherwise it writes rounded percentage coverage plus matched/missing skill evidence to results/<offer-match-id>.offer.json.

  5. The offer result retains bounded normalized offer text for later AI tailoring; GET /matches/<offer-match-id> omits this private field.

  6. The UI polls GET /matches/<offer-match-id> until the result is completed, unscorable, or failed.

Optional AI resume generation

  1. After a completed offer match, the UI explains that the redacted resume, skill evidence, and job-offer text will be sent to OpenRouter.

  2. The user must explicitly opt in before the UI submits POST /weights with the offer-match ID and consent affirmation.

  3. AIweighter publishes a persistent ID-only job to QUEUE_NAME.aiweight and returns an AI resume ID. The worker reads the redacted resume, skill result, and bounded normalized offer text from storage, then requests a Markdown resume from the configured model.

  4. The worker stores the versioned result at results/<weigh-id>.ai.json; the UI polls GET /weights/<weigh-id> and displays the returned Markdown as text for review or download.

  5. The prompt instructs the model to use only source-supported facts and omit unsupported qualifications, dates, achievements, or metrics. User-provided resume and offer content is treated as untrusted data, not instructions.

Extraction failures and retries

The extractor gives each job a five-minute processing timeout. A failed extraction is republished to the work queue with an incremented x-retry-count, then the original delivery is acknowledged. Piistripper and the skill matcher similarly retry processing failures. The initial attempt plus up to three retries means a job may be attempted four times at each stage. During redaction retries the status remains redacting and includes a retry message, keeping the UI progress step accurate.

A job still failing extraction is published to QUEUE_NAME.failed; a job still failing redaction is published to QUEUE_NAME.pii.failed; a job still failing skill matching is published to QUEUE_NAME.skills.failed. A job still failing offer matching is published to QUEUE_NAME.offers.failed. A job still failing AI resume generation is published to QUEUE_NAME.aiweight.failed.

Malformed job JSON is also sent directly to the failed queue.

Delivery semantics

The workflow is at-least-once, not exactly-once.

If a service stops between a side effect and acknowledgement, RabbitMQ can redeliver a job.

Result writes use deterministic keys (results/<job-id>.txt, results/<job-id>.redacted.txt, results/<job-id>.skills.json, and results/<offer-match-id>.offer.json), so repeated successful processing overwrites the corresponding object. The redacted copy does not replace the original extracted text.

There is no separate deduplication store, operation is idempotent.

SSE status durability

SSE status events are not a durable history for clients:

  1. they are consumed by the uploader,

  2. retained only in that uploader process.

A reconnect to the same live instance receives the latest snapshot, but an uploader after restart or another replica will not have the job’s status.

This is serious and needs proper addressing.
