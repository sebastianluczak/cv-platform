Processing status

RabbitMQ status queue, then uploader memory

QUEUE_NAME.events; in memory for at most 24 hours and up to 10,000 jobs per uploader process

The uploader consumes and acknowledges status messages. Its status history is lost when the process restarts.

Temporary files

The extractor downloads each input to a temporary file. For scanned PDFs it renders pages to temporary PNG files before OCR. The code removes these files after processing, but temporary data exists on the extractor host while a job is running.

Datacleaner service

The datacleaner service runs on a configurable interval (default: every 1 minute) to maintain data retention policies. It is stateless and does not participate in the main processing pipeline.

Purpose and scope

The datacleaner service performs two primary functions:

  1. S3 cleanup: Scans and deletes expired objects from configured S3-compatible storage:

    • Original uploaded files (uploads/<job-id>) after RETENTION_UPLOADS_DAYS days

    • Redacted text results (results/<job-id>.redacted.txt) after RETENTION_REDACTED_DAYS days

  2. RabbitMQ failed queue cleanup: Purges expired messages from failed queues:

    • <QUEUE_NAME>.extraction.failed

    • <QUEUE_NAME>.pii.failed

    • <QUEUE_NAME>.skills.failed

    • Other stage-specific failed queues

Messages are deleted after RETENTION_FAILED_QUEUE_DAYS days, allowing operators time to inspect and manually requeue failures if needed.

Cleanup interval and dry-run mode

The service runs cleanup cycles at a configurable interval (CLEANUP_INTERVAL_MINUTES, default: 1 minute). Each cycle:

  1. Scans S3 for expired objects

  2. Deletes expired S3 objects (unless DRY_RUN=true)

  3. Scans failed queues for expired messages

  4. Purges expired messages (unless DRY_RUN=true)

  5. Logs metrics and any errors

For testing and policy validation, the DRY_RUN environment variable logs what would be deleted without making any changes.

RabbitMQ failed queue retention

Failed messages (messages that exhausted retry attempts) are retained in dedicated failed queues for operator inspection. The datacleaner periodically purges messages older than RETENTION_FAILED_QUEUE_DAYS:

  • Operators can manually requeue failed messages for retry before expiration

  • After the retention period, messages are automatically deleted

  • The retention window allows time for incident investigation and diagnostics

See Processing Workflow for details on failure handling and retry semantics.

Operator configuration for production

Deploying datacleaner and configuring retention policies for production requires careful planning:

Required S3 permissions

The datacleaner service requires the following S3 IAM permissions on the configured bucket:

  • s3:ListBucket: List objects to identify candidates for deletion

  • s3:DeleteObject: Delete expired uploads and redacted text files

Example minimal bucket policy (adjust principals and conditions as needed):

{
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Service": "cv-platform-datacleaner" },
      "Action": ["s3:ListBucket", "s3:DeleteObject"],
      "Resource": [
        "arn:aws:s3:::cv-platform-uploads",
        "arn:aws:s3:::cv-platform-uploads/*"
      ]
    }
  ]
}

Compliance and data retention

Before deploying datacleaner to production, verify that configured retention periods comply with applicable data protection and privacy regulations:

  • Extracted text (results/<job-id>.txt) and skill results are not automatically deleted. If these contain personal data, configure S3 lifecycle policies separately or rely on datacleaner for redacted text cleanup only.

  • Redaction is best-effort: The redacted text may still contain sensitive information. Review redaction quality and retention periods in the context of your data protection obligations.

  • Original uploads are deleted after RETENTION_UPLOADS_DAYS. Ensure this period aligns with user expectations and legal requirements.

Testing retention policies

Before deploying to production, test retention policies using dry-run mode:

export DRY_RUN=true
export RETENTION_UPLOADS_DAYS=7
export RETENTION_REDACTED_DAYS=7
export RETENTION_FAILED_QUEUE_DAYS=7
./datacleaner

Dry-run mode logs what would be deleted without modifying S3 or RabbitMQ. Verify that the logged deletions match your intended retention policy.

Additional retention considerations

The offer matcher does not persist fetched offer HTML. Pasted offer text is carried in its durable RabbitMQ message until processing; configure queue retention accordingly. The offer matcher API has no user authorization or ownership model, so deployments must keep it behind an access-controlled boundary.

After a user opts in, normalized offer text and generated Markdown persist as result artifacts, and the redacted resume and skill result are sent to the configured external OpenRouter model. Redaction is best-effort and does not guarantee anonymity. AIweighter and offermatcher do not implement authentication or ownership checks; keep both APIs behind an access-controlled boundary. Configure object-store lifecycle and access controls for all resume, offer, and AI output artifacts.

Storage administrators must configure lifecycle expiration and access controls appropriate to their data policy. Review Data Security (PII) for additional security and privacy considerations.
