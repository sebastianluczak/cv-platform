= Go Services Refinement Backlog
:toc:
:toclevels: 2

This backlog turns the services refinement plan into developer-ready work items
for the nine Go modules under `services/`. Ticket keys below are proposed
placeholders; replace them with the project's Jira project key when importing.
Priorities are proposed (`P1` first, `P2` next, `P3` owner/decision-dependent);
map them to the Jira project's configured priority scale during import.

== Scope and delivery rules

The first tickets are deliberately small and service-local. Queue, retry,
acknowledgement, retention, and client-visible status behavior are contracts:
add or update focused tests before changing them. Preserve the pipeline order:
persist stage output, publish the next-stage job with broker confirmation, then
acknowledge the current delivery. Processing remains at-least-once.

Each service is an independent Go module. Run Go commands from the affected
module, for example `go -C services/piistripper test ./...`. Run `sh test.sh`
for changes that cross service boundaries. A shared `services/common` change
must also be tested against its affected consumers.

The API authentication/ownership gap is documented separately and is not
included as a junior refactoring ticket. Keep affected APIs behind the
access-controlled application boundary; do not expose them directly to
untrusted networks.

== Tickets

=== CVPS-101 — Use the configured metrics port for each service

*Type:* Bug

*Priority:* P1

*Components:* `uploader`, `extractor`, `piistripper`, `skillmatcher`,
`offermatcher`, `datacleaner`

*Depends on:* None

*Description:* Six service entry points start the shared metrics server with
`METRICS_PORT_AIWEIGHTER` instead of their own configured port. Use the
service-specific environment variable so each process binds to its intended
metrics endpoint.

*Acceptance criteria:*

* `services/uploader/uploader.go` uses `METRICS_PORT_UPLOADER`.
* `services/extractor/consumer.go` uses `METRICS_PORT_EXTRACTOR`.
* `services/piistripper/main.go` uses `METRICS_PORT_PIISTRIPPER`.
* `services/skillmatcher/main.go` uses `METRICS_PORT_SKILLMATCHER`.
* `services/offermatcher/main.go` uses `METRICS_PORT_OFFERMATCHER`.
* `services/datacleaner/main.go` uses `METRICS_PORT_DATACLEANER`.
* AIweighter and roleinsights continue to use their own service-specific
  variables.
* With each corresponding port configured, each service exposes `/metrics` on
  that port and does not contend for AIweighter's port.

*Validation:* Run focused tests/builds for affected modules. Smoke-test metrics
port selection for the six corrected services without requiring external
RabbitMQ or object storage dependencies.

*Type:* Chore
*Priority:* P1
*Components:* `roleinsights`, repository build configuration
*Depends on:* None

*Description:* `services/roleinsights/roleinsights` is a tracked Linux ELF

*Acceptance criteria:*

*Validation:* Search build/deployment references, then run

=== CVPS-103 — Test datacleaner failed-queue cleanup behavior

*Type:* Test
*Priority:* P1
*Components:* `datacleaner`
*Depends on:* None

*Description:* Replace tests that only reproduce calculations or log that
cancellation works with tests that exercise the queue cleanup implementation.
Add only the smallest seam needed to test broker operations; tests must not
require a live RabbitMQ server.

*Acceptance criteria:*

* Tests exercise cleanup of an expired message and retention of a recent
  message.
* Tests cover timestamp extraction and the current conservative behavior for
  messages with missing or invalid timestamps; such messages are not treated as
  expired.
* Dry-run tests verify that an expired message is retained and no delete
  acknowledgement is sent.
* Cancellation and queue-operation failures are exercised and their results
  are asserted.
* Tests assert observable outcomes (ack/nack, queue selection, errors or
  returned counts), not duplicate the implementation's age arithmetic.

*Validation:* Run `go -C services/datacleaner test ./...` and
`go -C services/datacleaner test -race ./...`.

=== CVPS-104 — Make datacleaner queue coverage and summaries accurate

*Type:* Bug
*Priority:* P1
*Components:* `datacleaner`
*Depends on:* CVPS-103

*Description:* Align RabbitMQ cleanup with the documented failed-queue set and
make cleanup results observable. The current failed queue list omits
`<QUEUE_NAME>.roleinsights.failed`; an obsolete TODO says queue cleanup is
unimplemented; error paths are logged but can still return success; and the
cycle summary uses counters that are never updated.

*Acceptance criteria:*

* The stale TODO is removed and the cleanup implementation is accurately
  described.
* The queue set includes every documented stage failed queue, including
  `<QUEUE_NAME>.roleinsights.failed`, without targeting work or status queues.
* Per-queue failures are returned or otherwise surfaced to the cleanup cycle;
  one queue failure does not prevent attempting the remaining queues.
* Summary counters reflect actual deleted/purged messages and failures.
* Dry-run, retention cutoff, retry-safe acknowledgements, and current cleanup
  semantics remain covered by tests from CVPS-103.

*Validation:* Run `go -C services/datacleaner test ./...`; review test cases
against the queue list in `docs/cv-analyzer/modules/architecture/pages/`.

=== CVPS-105 — Lock down core pipeline handoff behavior

*Type:* Test
*Priority:* P1
*Components:* `extractor`, `piistripper`, `skillmatcher`, `common/rabbitmq`
*Depends on:* None

*Description:* Add focused tests for the core upload-processing consumers so
future cleanup or shared-helper work cannot silently change delivery
guarantees. Test current behavior first; do not change queue contracts in this
ticket.

*Acceptance criteria:*

* Extractor tests prove extracted output is persisted before a confirmed
  redaction-job publish, and the source delivery is acknowledged only after
  that publish is confirmed.
* Piistripper tests prove redacted output is persisted before a confirmed
  skill-job publish, and the source delivery is acknowledged only after
  confirmation.
* Skillmatcher tests prove result persistence precedes the completed status
  event and acknowledgement follows the required publish confirmation.
* Publish errors, rejected/timeout confirmations, and acknowledgement errors
  are covered for relevant handoffs; failed publishes do not result in a
  success acknowledgement.
* Retry counts remain bounded at the initial attempt plus three retries;
  malformed and exhausted jobs are routed to their existing stage-specific
  failed queues.
* Tests do not need live RabbitMQ or S3-compatible storage.

*Validation:* Run `go -C services/extractor test ./...`,
`go -C services/piistripper test ./...`,
`go -C services/skillmatcher test ./...`, and
`go -C services/common test ./...`.

=== CVPS-106 — Define and test worker shutdown behavior

*Type:* Reliability
*Priority:* P2
*Components:* `extractor`, `piistripper`, `skillmatcher`, `offermatcher`,
`aiweighter`, `roleinsights`
*Depends on:* CVPS-105

*Description:* Review how each long-running consumer handles SIGTERM/SIGINT
and in-flight jobs. Implement a consistent, tested shutdown path that stops
taking new work and allows bounded operations to finish or safely return work
to RabbitMQ. Do not acknowledge a delivery if its required persistence or
confirmed handoff did not complete.

*Acceptance criteria:*

* Each listed consumer has an explicit shutdown path driven by a signal-aware
  context.
* New deliveries stop being processed during shutdown.
* In-flight network/storage/model work has a bounded cancellation or completion
  policy; unacknowledged work remains eligible for at-least-once redelivery.
* Acknowledgement and publisher-confirm ordering remain unchanged.
* Tests cover shutdown with no in-flight job and shutdown during a bounded
  in-flight operation.
* Service documentation describes the resulting shutdown behavior.

*Validation:* Run tests for all affected modules and `sh test.sh` if shared
consumer or queue behavior changes.

=== CVPS-107 — Extract only proven-identical worker delivery mechanics

*Type:* Refactor
*Priority:* P2
*Components:* `extractor`, `piistripper`, `skillmatcher`, `offermatcher`,
`aiweighter`, `roleinsights`, `common`
*Depends on:* CVPS-105

*Description:* Compare the six workers' retry, failed-queue, status, and
acknowledgement paths. Extract a shared helper only where CVPS-105 and existing
module tests prove that behavior is identical. Keep domain-specific job
validation and result processing in the owning service.

*Acceptance criteria:*

* The refactor removes demonstrated duplication without introducing a generic
  framework or unnecessary dependencies.
* Service-specific message validation, status text, persistence, and retry
  policy remain explicit.
* At-least-once delivery, retry limits, failed queue routing, publish confirms,
  and persist/publish/ack order are unchanged.
* Tests cover both successful and failing delivery paths in every affected
  module.
* Shared-code changes are tested against all affected consumers.

*Validation:* Run focused module tests and `sh test.sh` for any cross-module
change.

=== CVPS-108 — Agree an artifact-retention matrix

*Type:* Spike
*Priority:* P3
*Components:* `datacleaner`, `common`, architecture documentation, data-policy
owners
*Depends on:* Data-policy owner review

*Description:* Document a complete retention decision before extending
deletion behavior. Include original uploads, extracted and redacted text,
skill scores, offer-match data, AI outputs, and failed queue messages. Identify
the authoritative policy owner and whether expiration belongs in datacleaner,
object-store lifecycle rules, queue TTL, or another approved mechanism.

*Acceptance criteria:*

* A reviewed matrix names each artifact/message type, its storage location,
  approved retention period, deletion mechanism, and accountable owner.
* Existing retention behavior and uncovered artifact types are called out.
* The matrix is consistent with the applicable data policy and architecture
  documentation.
* No deletion behavior changes as part of this spike; implementation work is
  proposed as a separate ticket after approval.

*Validation:* Obtain data-policy owner approval and update/link the relevant
architecture and operational documentation.

=== CVPS-109 — Design durable status recovery and fan-out

*Type:* Spike
*Priority:* P3
*Components:* `uploader`, `common/rabbitmq`, architecture documentation,
deployment owners
*Depends on:* Deployment-owner review

*Description:* The uploader's progress snapshot is in-memory, is lost on
restart, and is not shared among replicas. Document viable designs for clients
to recover current status and for all serving replicas to observe updates.
Define the behavior before selecting a persistence or messaging change.

*Acceptance criteria:*

* The design states client-visible recovery behavior after reconnect and
  uploader restart, including terminal jobs and unknown/expired job IDs.
* At least two viable approaches are compared for durability, multi-replica
  delivery, operational complexity, and data retention.
* The proposal addresses duplicate and out-of-order status events.
* Deployment owners approve the direction; no storage or broker behavior is
  changed in this spike.
* An approved implementation is split into separate tickets covering contract,
  migration, tests, operations, and documentation.

*Validation:* Review the proposal with deployment owners and update the
processing/status architecture documentation after a decision.
